ReliefPlan AI
AI-Powered Emergency Resource Allocation & Decision Support System
Complete project guide: purpose, flow, user inputs, processing, outputs, formulas, dashboard pages, testing, demo and viva preparation. Python course project.
1. Project Overview
ReliefPlan AI helps an emergency manager decide where limited relief supplies (food, water, medical kits) should go after a disaster. The user describes the disaster and the supplies on hand. The system predicts how many people will be affected in each area, ranks areas by priority, calculates shortages, computes a fair allocation with an optimizer, explains the reasoning, and lets the user test what-if changes.
One-line pitch
A system that predicts where a disaster will hit hardest, then calculates the best way to split limited supplies, and explains why.
Why it is a strong project
Predict, then optimize: an ML model feeds a linear-programming optimizer, so the project turns predictions into decisions.
Fairness rule: every area keeps a minimum share of its need, so no area receives nothing.
Explainable: SHAP and a priority-score breakdown show why an area was rated critical.
Proven: the plan is compared with a simple equal-split baseline and the improvement is calculated, not typed in.
Interactive: users enter inputs and test what-if scenarios on a dashboard.

5. Formulas
Priority score
priority_i = w1*norm(impact_i) + w2*norm(predicted_demand_i)
+ w3*norm(shortage_i) + w4*norm(medical_need_i)
+ w5*accessibility_penalty_i
w1 to w5 are weights that sum to 1 and come from a config file or sidebar sliders. norm() is min-max scaling inside the current scenario. Use only features that exist in your data.
Note: These thresholds are adjustable defaults, not scientific constants.
Demand, shortage and coverage
demand_ik   = predicted_people_i * need_per_person_k * (duration / 72)
shortage_ik = max(0, demand_ik - available_ik)
coverage_k  = total_available_k / total_demand_k
Optimizer (linear programming)
Variable: x_ik = amount of resource k sent to area i, with x_ik at least 0.
Maximise   sum over i and k of  priority_i * x_ik / demand_ik
Subject to sum over i of x_ik <= supply_k      (never send more than you have)
x_ik <= demand_ik                   (never send more than an area needs)
x_ik >= floor * demand_ik           (fairness: every area keeps a minimum)
If warehouse and distance data exist, extend to a transportation problem with a cost term. If not, show the message: Source optimization unavailable, no warehouse data.
Impact of optimization
baseline_i  = supply_k * demand_ik / total_demand_k   (equal share by need)
reduction %  = (shortage_before - shortage_after) / shortage_before * 100
Because both plans spend the same total supply, compare the shortage in critical and high priority areas, and the coverage of those areas. That is where the optimizer helps.
Worked example (illustrative numbers)
Water supply is 100 units. Minimum coverage is 25%. Three areas:
Unmet need in critical and high areas: equal split = (50 - 33.3) + (60 - 40) = 36.7. AI plan = 0 + 20 = 20. Reduction = (36.7 - 20) / 36.7 = about 45%. The low-priority area still receives its 25% minimum.

12. Model Evaluation
Choose the best model by a stated metric (F1 or PR-AUC when classes are imbalanced). Use a stratified split, cross-validation and a fixed random seed. Do not rely on accuracy alone.
13. Testing Checklist
Allocation never exceeds supply.
Allocation never exceeds an area's demand.
Coverage stays between 0 and 100%.
Priority scores stay between 0 and 1.
Zero supply is handled without errors.
The same inputs always give the same outputs.
Changing a what-if slider changes the result in the expected direction.
No page shows NaN, undefined, infinity or empty cards.
Every audit entry contains inputs, model, allocation and solver status.

16. Limitations and Responsible Use
This is a decision-support tool. Final decisions rest with emergency managers.
Predictions are only as good as the dataset and are never certain.
Per-person needs, weights and thresholds are assumptions and are labelled as such.
SHAP describes how the model behaves. It does not prove cause and effect.
Simulated results are not real-world outcomes.
Warehouse routing is not available without distance data.
Label every output on screen as PREDICTION, OPTIMIZATION, SIMULATION or RECOMMENDATION.

Question | Short answer
Why this model? | It scored best on the stated metric (F1 or PR-AUC) in cross-validation; see metrics.json.
Why linear programming? | The goal and limits are linear, LP is fast and its status shows whether the result is truly optimal.
What does SHAP show? | How much each feature pushed an area's prediction up or down.

Term | Meaning
Coverage | Share of need that is met: available divided by required.
Shortage | Unmet need: demand minus available, never below zero.
Priority score | A number from 0 to 1 ranking how urgent an area is.
LP (linear programming) | A method for finding the best values under linear limits.
SHAP | A method that explains each feature's contribution to a prediction.
What-if | Rerunning the analysis with changed inputs.
